## Overview

Training a model is only ~20% of the work. This lesson dives into MLOps — the discipline of deploying, monitoring, and maintaining ML systems in production. You'll learn the core pipeline stages, tooling choices, and automation levels that separate prototype notebooks from reliable, scalable ML services.

## 💡 Why MLOps Exists: The Production Gap

Most ML projects never reach production. Google's famous 2015 paper *Hidden Technical Debt in Machine Learning Systems* revealed that **model code represents only 5-10% of a real ML system**. The rest is:

| Component | Examples |
|---|---|
| Data pipelines | Ingestion, validation, feature engineering |
| Infrastructure | Serving, scaling, GPU orchestration |
| Monitoring | Data drift, model degradation, latency |
| Governance | Versioning, audit trails, reproducibility |
| CI/CD | Automated testing, retraining, deployment |

MLOps applies **DevOps principles** (CI/CD, IaC, monitoring) to ML-specific challenges like data versioning, experiment tracking, and model decay.

> **The production gap**: A model that achieves 95% accuracy in a notebook but can't handle 1,000 req/s, doesn't detect data drift, or can't be rolled back is not a production model — it's a prototype.

## 💡 The MLOps Maturity Model

Google defines three levels of MLOps maturity. Most teams sit at Level 0 and wonder why models fail silently in production.

### Level 0: Manual Process
- Data scientists train models in notebooks
- Manual handoff to engineering for deployment
- No automated retraining, no monitoring
- **Problem**: Model staleness, no reproducibility

### Level 1: ML Pipeline Automation
- End-to-end pipeline: data → train → validate → deploy
- Automated retraining triggered by schedule or drift
- Feature store for consistent feature engineering
- **Gain**: Continuous training, faster iteration

### Level 2: CI/CD for ML
- Pipeline code is tested, versioned, and deployed via CI/CD
- Automated testing of data, model quality, and serving infra
- A/B testing and canary deployments for model rollout
- **Gain**: Rapid, reliable experimentation at scale

> Most organizations should target **Level 1** before attempting Level 2. Premature optimization of the pipeline itself creates complexity without payoff.

## 💡 Anatomy of an ML Pipeline

A production ML pipeline has **seven canonical stages**. Each must be automated, versioned, and observable.

1. **Data Ingestion** — Pull from sources (databases, APIs, streams). Tools: Apache Airflow, Prefect, Dagster.
2. **Data Validation** — Schema checks, statistical tests, anomaly detection. Tools: Great Expectations, TensorFlow Data Validation (TFDV).
3. **Feature Engineering** — Transform raw data into model inputs. Tools: Feast (feature store), dbt, Spark.
4. **Model Training** — Train with tracked hyperparameters and metrics. Tools: MLflow, Weights & Biases, SageMaker.
5. **Model Evaluation** — Compare against baseline, check fairness/bias. Tools: MLflow, Evidently AI.
6. **Model Registry** — Version, approve, stage models. Tools: MLflow Model Registry, Vertex AI Model Registry.
7. **Model Serving** — Deploy as API endpoint, batch job, or edge. Tools: TensorFlow Serving, Seldon, BentoML, KServe.

Each stage emits **metadata** (lineage, metrics, artifacts) that feeds the monitoring and governance layer.

## 🌟 The Factory Floor Analogy

Think of an ML pipeline as a **car manufacturing plant**.

- **Raw materials** (steel, rubber) = raw data
- **Quality inspection of incoming materials** = data validation
- **Machining parts to spec** = feature engineering
- **Assembly line** = model training
- **Quality control at end of line** = model evaluation
- **Warehouse with part numbers** = model registry
- **Dealership delivering cars to customers** = model serving

A factory doesn't stop after building one car. It **continuously produces** while monitoring quality at every station. If a batch of steel is defective (data drift), the line halts before producing defective cars (bad predictions). MLOps is the discipline of running this factory — not just building a single prototype car in a garage.

## 💻 Hands-On: MLflow Pipeline in 50 Lines

Here's a minimal but production-aware training pipeline using MLflow for experiment tracking and model registry:

```python
import mlflow
import mlflow.sklearn
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split
from sklearn.metrics import accuracy_score, f1_score
from sklearn.datasets import load_wine
import warnings
warnings.filterwarnings('ignore')

# --- Stage 1: Data Ingestion ---
data = load_wine()
X_train, X_test, y_train, y_test = train_test_split(
    data.data, data.target, test_size=0.2, random_state=42
)

# --- Stage 2: Data Validation (simplified) ---
assert X_train.shape[1] == 13, "Feature count mismatch — schema violation!"
assert len(set(y_train)) == 3, "Expected 3 classes"

# --- Stages 3-5: Train, Evaluate, Register ---
mlflow.set_experiment("wine-classifier")

with mlflow.start_run(run_name="rf-baseline") as run:
    # Hyperparameters
    params = {"n_estimators": 200, "max_depth": 10, "random_state": 42}
    mlflow.log_params(params)
    
    # Train
    model = RandomForestClassifier(**params)
    model.fit(X_train, y_train)
    
    # Evaluate
    preds = model.predict(X_test)
    acc = accuracy_score(y_test, preds)
    f1 = f1_score(y_test, preds, average="weighted")
    mlflow.log_metrics({"accuracy": acc, "f1_weighted": f1})
    
    print(f"Accuracy: {acc:.4f} | F1: {f1:.4f}")
    
    # Register model if quality gate passes
    if acc >= 0.90:
        mlflow.sklearn.log_model(
            model,
            artifact_path="model",
            registered_model_name="wine-classifier-prod"
        )
        print("✅ Model registered to MLflow Model Registry")
    else:
        mlflow.sklearn.log_model(model, artifact_path="model")
        print("⚠️  Model logged but NOT promoted — below quality gate")
```

**To run:**
```bash
pip install mlflow scikit-learn
python train.py
mlflow ui  # Open http://localhost:5000 to inspect runs
```

Notice the **quality gate** at line 42: the model only enters the registry if accuracy ≥ 0.90. This is a minimal version of the automated evaluation gates in Level 1+ pipelines.

## 💡 The MLOps Tooling Landscape

The ecosystem is crowded. Here's a pragmatic decision matrix:

| Capability | Open Source | Managed Cloud |
|---|---|---|
| **Orchestration** | Airflow, Prefect, Kubeflow Pipelines | AWS Step Functions, Vertex Pipelines |
| **Experiment Tracking** | MLflow, W&B (free tier) | SageMaker Experiments, Azure ML |
| **Feature Store** | Feast, Hopsworks | Vertex Feature Store, SageMaker Feature Store |
| **Model Serving** | BentoML, Seldon, KServe | SageMaker Endpoints, Vertex Prediction |
| **Monitoring** | Evidently, Whylogs, NannyML | SageMaker Model Monitor, Fiddler |
| **Data Versioning** | DVC, LakeFS | Delta Lake (Databricks) |

> **Expert tip**: Start with **MLflow + Airflow + Evidently** for a lean, vendor-neutral stack. Migrate to managed services only when operational overhead justifies the cost.

### Common Anti-Patterns
- ❌ **"We'll add monitoring later"** — Drift kills models silently within weeks
- ❌ **Pickle files on S3** — No versioning, no lineage, no rollback
- ❌ **One mega-notebook** — Untestable, unreproducible, undeployable
- ❌ **Ignoring data tests** — 90% of ML failures are data failures, not code failures

## 💻 Monitoring: Catching Silent Failures

Traditional software either works or crashes. ML systems **degrade silently**. Three monitoring pillars:

### 1. Data Drift
Input feature distributions shift from training data. Example: an e-commerce model trained on pre-COVID shopping patterns fails post-COVID.

```python
# Using Evidently for drift detection
from evidently.report import Report
from evidently.metric_preset import DataDriftPreset
import pandas as pd

reference = pd.DataFrame(X_train, columns=data.feature_names)
current = pd.DataFrame(X_test, columns=data.feature_names)

report = Report(metrics=[DataDriftPreset()])
report.run(reference_data=reference, current_data=current)
report.save_html("drift_report.html")
# Automate: trigger retraining if >30% features drift
```

### 2. Model Performance Decay
Track prediction quality over time using **ground truth feedback loops**. If labels arrive delayed (e.g., fraud confirmed 30 days later), use proxy metrics: prediction confidence distribution, prediction class ratios.

### 3. Infrastructure Health
- Latency p50/p95/p99 per prediction
- Throughput (requests/sec)
- Error rates, GPU utilization
- Use Prometheus + Grafana or cloud-native equivalents

## Key Concepts

| Term | Definition |
|------|------------|
| **MLOps** | The discipline of deploying, monitoring, and maintaining ML models in production by applying DevOps principles to the ML lifecycle. |
| **Feature Store** | A centralized repository for storing, versioning, and serving precomputed features, ensuring consistency between training and serving. |
| **Model Registry** | A versioned catalog of trained models with metadata (metrics, lineage, stage) that governs which model is promoted to production. |
| **Data Drift** | A change in the statistical distribution of input features compared to the training data, which can degrade model performance without any code change. |
| **Quality Gate** | An automated checkpoint that evaluates a candidate model against predefined metrics and only promotes it to production if thresholds are met. |
| **Experiment Tracking** | The practice of logging hyperparameters, metrics, artifacts, and code versions for every training run to enable comparison and reproducibility. |

## Real-World Analogy

> An ML pipeline is like a car manufacturing plant. Raw materials (data) arrive and are inspected (validation), machined into parts (feature engineering), assembled (training), quality-checked (evaluation), catalogued with serial numbers (model registry), and delivered to customers (serving). The plant runs continuously, and quality inspectors at every station catch defects before they reach the customer. MLOps is the discipline of running this factory — not just hand-building a single prototype in a garage.

## Today's Takeaways

- [ ] Model training is ~20% of production ML; the rest is pipelines, monitoring, infrastructure, and governance — MLOps addresses this gap.
- [ ] Target MLOps Level 1 (automated pipelines with continuous training) before Level 2 (CI/CD for pipeline code itself).
- [ ] Monitor three pillars in production: data drift, model performance decay, and infrastructure health — ML systems fail silently.

- A) Automated ML pipeline with continuous training
- B) Using GPUs instead of CPUs for training
- C) Deploying models as REST APIs
- D) Storing models in a cloud object store

**Answer: A) Automated ML pipeline with continuous training**

Level 0 is characterized by manual, ad-hoc processes where data scientists hand off models to engineers. Level 1's defining leap is an automated, end-to-end ML pipeline that enables continuous training — triggered by schedule or data drift. Using GPUs (B), REST APIs (C), and cloud storage (D) are infrastructure choices that can exist at any maturity level and don't address the core automation gap.
